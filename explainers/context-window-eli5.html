Memory and the context window

A chatbot seems to remember your conversation. It does not. Before every reply, the whole chat is sent to the model again, and the model can only read a fixed number of tokens at once: its context window. This part shows what fits, what falls out, why a longer window costs more, and why even text in view can be missed.

A topic study built from the primary sources: Liu and others’ “Lost in the Middle” (2023), Su and others’ RoPE paper (2021), Lewis and others’ retrieval-augmented generation paper (2020), the 2017 Transformer paper, Meta’s Llama 3 report, the vLLM paper on the KV cache, Chen and others’ Position Interpolation paper (2023), and Anthropic’s API documentation as of November 2026; every number below was checked against them · Read the main source ↗

The problem

The model keeps nothing between replies

Part 2 showed that a chat is one long document the model continues. Here is the catch: nothing about your chat is kept inside the model between replies. Its learned numbers never change while you talk. So for every new reply, the app sends the whole conversation again.

Anthropic’s documentation says it plainly: “The Messages API is stateless, which means that you always send the full conversational history” public. Each request holds all earlier turns plus the new message, and the reply becomes part of the next request. In a 20-turn chat, your first message is sent 20 times.

Go deeper: is all that re-reading wasted?

Mostly not. Servers can keep the work done on an unchanged start of the conversation and reuse it, called prompt caching; the bonus study, Inside LLM serving, covers it. Anthropic’s documentation adds that cached text “still occupies the context window”: caching changes the price, not what fits public.

The analogy

A reader with a fixed-size desk

Picture a reader who answers letters but keeps no notebook. Before each reply they read every page on their desk, top to bottom. The desk holds only so many pages. When a new page arrives and the desk is full, the oldest page goes in the bin.

Mapping it back: the pages are the chat’s tokens, the desk is the context window, the bin is text dropped from the request. Where the analogy breaks: the model reads the whole desk in one parallel pass (Part 9), not page by page, and it cannot see the bin at all, so it never knows what it lost.

The building block

Everything shares one window, even the reply

The window is measured in tokens, Part 1’s word pieces, about four characters of English each. Anthropic defines it as “all the text a language model can reference when generating a response, including the response itself” public. So the reply needs room too.

Anthropic’s list of what counts: the system prompt, every message including documents, images and tool results, the tool definitions, and the reply, with any thinking public. The split drawn here is made up example. A long document attached to a chat leaves less room for the chat itself.

The running example

Anaya’s chat grows turn by turn

Follow one chat for the rest of this part. In turn 1, Anaya writes “I’m Anaya, and I’m allergic to peanuts.” Then she plans a trip with the assistant. Each turn, her message plus the reply, adds a few hundred tokens example. The window here holds 8,000 tokens.

The turns average 600 tokens, so after 20 turns the chat is 12,000 tokens long example. At turn 14 it no longer fits: 8,400 tokens against a window of 8,000. Something has to give. In the lab below, the same chat keeps growing, and you choose the window.

At the limit

Three things an app can do

When a chat outgrows the window, the model itself cannot help: it only reads what it is sent. The choice is made by the software around it, and there are three common answers.

Refuse: if the input alone is too big, Anthropic’s API returns an error, “prompt is too long” public. Drop the oldest: Anthropic notes chat apps such as claude.ai “can also manage the context window on a rolling ‘first in, first out’ basis” public. Summarise: its compaction feature “replaces the older turns of a conversation with a summary” public. Exactly which app does what, when, is mostly not documented not public.

The wrong intuition

Forgetting is a cliff, not a fade

People forget gradually: old memories blur. So it is natural to assume a model’s grip on early turns weakens slowly. For text that has left the window, that is wrong. It is not faint. It is simply not in the request.

If turn 1 is dropped, Anaya’s allergy is gone completely, and nothing marks the gap. Ask for a snack idea and the model answers from what is in view, which no longer mentions peanuts. Inside the window things are less tidy than this step suggests; chapter 12 shows that text in view can still be missed.

The cost of seeing more

Twice the text, four times the comparisons

Why not just make the window huge? Part 7 gave the first reason. Reading a text, every token compares itself with itself and every earlier token, in every head of every layer. Each dot below is one comparison example:

For n tokens that is n × (n + 1) ÷ 2 comparisons, so doubling the text roughly quadruples them; the 2017 Transformer paper lists attention’s cost per layer as growing with n² public. At 128,000 tokens that is 8.2 billion per head per layer. Llama 3 8B has 32 layers of 32 heads, 1,024 in all public: about 8.4 trillion comparisons to read one full window example.

Go deeper: why Meta trained long text last

Meta’s Llama 3 report says it did not train on long sequences earlier “because the compute in self-attention layers grows quadratically in the sequence length”. It trained with an 8K-token window, then lengthened it in six stages to 128K at the end, using about 800 billion tokens for that stage public. Adding one new token to a chat of n tokens costs only n comparisons per head per layer, which is why each new word of a reply is cheaper than reading the whole chat; the comparisons still grow with the chat, as Part 9 counted.

The cost of seeing more

The KV cache grows with every token

The second reason is memory. Part 7 showed that each token’s keys and values are saved, so later tokens can compare against them: the KV cache. It holds one key and one value per token, per layer, per key-value head, and it lives in the chip’s scarce memory (Part 8).

Size per token = 2 (key and value) × layers × key-value heads × numbers per head × bytes per number. That is the vLLM paper’s formula: its 13-billion-number example needs 800 KB per token, up to 1.6 GB for one 2,048-token request public. For Llama 3 8B, 32 layers × 8 heads × 128 numbers × 2 bytes × 2 = 128 KB per token public. At 128,000 tokens, one chat’s cache is bigger than the model’s own weights.

Go deeper: where the numbers come from

Llama 3’s report lists 32, 80 and 126 layers for its 8B, 70B and 405B models, each with 8 key-value heads, and widths of 4,096, 8,192 and 16,384 shared among 32, 64 and 128 query heads: 128 numbers per head in all three public. At 2 bytes per number that is 131,072, 327,680 and 516,096 bytes per token. The 8B model’s 8,030,261,248 weights (Part 9) take about 16.1 GB. The bars assume 16-bit numbers; servers can shrink caches with 8-bit numbers and other tricks, which the bonus study covers example.

Go deeper: exactly what the lab computes

Turn i has round(average × pattern) tokens, pattern 0.6, 1.4, 0.8, 1.2, 1.0 repeating example. Counting back from the newest turn, whole turns are kept while their total fits the window; the rest fell out. Nothing is reserved for the reply or a system prompt. Comparisons to read the n tokens in view = layers × query heads × n(n + 1) ÷ 2. KV cache = n × 2 × layers × 8 × 128 × 2 bytes, with layers and heads from Llama 3’s report public. Gigabytes are 10⁹ bytes. The windows run from 2,000 to 128,000 tokens; Llama 3’s published maximum is 128K public.

Knowing where

Each token’s position is a turning angle

A window is not just a bag of tokens: order matters. Part 7 met the usual method, rotary position embedding (RoPE). Each query and key is cut into pairs of numbers, and each pair is turned by an angle that grows with the token’s position, some pairs fast, some slowly public.

Su and others’ paper: RoPE “encodes the absolute position with a rotation matrix and meanwhile incorporates the explicit relative position dependency” public. Positions 1 and 3 differ by the same angle as 5 and 7, so a score depends on how far apart two tokens are. Llama 3 uses RoPE, and raised its base setting to 500,000 “to better support longer contexts” public.

Go deeper: the angles

Pair number i of a list d numbers long turns by position × base−2i/d radians. With the original base of 10,000, the first pair turns about one radian per position and the last pairs barely move. The RoPE paper shows this setting gives a “long-term decay”: the inner product tends to shrink as tokens get further apart public. A bigger base slows every pair down, so far-apart positions stay distinguishable over longer texts. The 40° and 10° steps drawn here are made up example.

Making room

Stretching a window after training

A model trained on short texts has never seen large position numbers. Feed it longer text and the far positions are uncharted. Chen and others at Meta found a cheap fix for RoPE models: squeeze the new, longer range of positions back into the range the model was trained on public.

Their Position Interpolation “linearly down-scales the input position indices to match the original context window size”, extending LLaMA models’ 2,048-token windows “to up to 32768 with minimal fine-tuning (within 1000 steps)” public. Later methods such as YaRN refine the squeeze; its authors report needing 10 times fewer tokens and 2.5 times fewer training steps than earlier methods public.

The surprise

Lost in the middle

Being in the window is not the same as being used. Liu and others gave models a question and 20 short Wikipedia passages, about 4,000 tokens, exactly one holding the answer. Then they moved that passage from first to last and measured how often the answer came out right public.

The curve is a U: best at the start and end, worst in the middle. The paper’s words: GPT-3.5-Turbo’s accuracy “can drop by more than 20%—in the worst case, performance in 20- and 30-document settings is lower than performance without any input documents (i.e., closed-book performance; 56.1%)” public. Here, 75.8% at the start against 53.8% in the middle is 22 percentage points.

Go deeper: what exactly was measured

The questions came from NaturalQuestions-Open, real Google searches with answers marked in Wikipedia. Passages were at most 100 tokens; the 19 decoys were the most relevant passages that did not contain the answer. A reply counted as correct if any accepted answer appeared in it public. The models were 2023 versions of GPT-3.5-Turbo, Claude 1.3, MPT-30B-Instruct and LongChat-13B. In a second, simpler test, finding a key in a list of key-value pairs, Claude 1.3 was nearly perfect at every position while others again sagged in the middle public. The paper did not test today’s models; Anthropic’s documentation says of current ones that “as token count grows, accuracy and recall degrade, a phenomenon known as context rot” public.

The common mistake

A bigger window is not better reading

It is tempting to think a model with a bigger window reads better. The same paper tested this directly: GPT-3.5-Turbo with a 4K-token window against its 16K-token version, on the 20-passage test that fits in both public.

The bars are nearly identical at every position. The paper: “Extended-context models are not necessarily better at using input context” public. A bigger window lets more text in; it does not change how well the text already in view is used. Anthropic’s own advice: “more context isn’t automatically better” public.

The workaround

Fetch only the pages you need

If the window is limited and the middle gets lost, send less. Retrieval keeps a large library outside the model, finds the few passages that match the question, and puts just those into the window. Lewis and others named this retrieval-augmented generation, RAG, in 2020 public.

Their library was Wikipedia cut into 21 million 100-word chunks, searched with a learned retriever, with 5 or 10 passages fetched per question public. Swap the library and the answers change: with a 2016 index RAG named 70% of 2016 world leaders correctly, with a 2018 index 68% of 2018 ones, and only 4% to 12% with the mismatched index public.

Go deeper: more is not always better here either

Liu and others also ran the full pipeline: retrieve from Wikipedia, then answer. Accuracy “saturates long before retriever recall saturates”: using 50 retrieved passages instead of 20 improved GPT-3.5-Turbo by only about 1.5% public. Fetching the right few matters more than fetching many.

Memory features

“Memory” is notes put back in view

Some assistants remember you across chats. The model still learns nothing between them. Instead, notes are saved outside it, as ordinary text, and read back into a later chat’s window. It is retrieval again, with your own past as the library.

Anthropic’s memory tool is documented this way: Claude stores what it learns “in files under /memories and reads them back in later conversations”, and the files live in the developer’s application, not the model public. A summary from compaction works the same way inside one chat. Both cost window space when read back in.

As of today

Windows grew almost 500 times

Windows have grown fast. LLaMA’s inputs in early 2023 had to be “fewer than 2048 tokens”; the Lost in the Middle paper tested 4K, 16K and 100K versions; Llama 3 reached 128K public. Anthropic’s documentation lists a 1,000,000-token window for its current models public.

From 2,048 to 1,000,000 tokens is about 490 times. As of November 2026, Anthropic lists 1M tokens for its current Opus, Sonnet and Haiku models among others, and 200K for older ones, with up to 128,000 tokens of output per request public. Every chapter above still applies: a million-token window is a bigger desk, not a better memory.

Window sizes change with almost every model release. The sizes here are what each paper or vendor document stated; check the vendor’s current documentation before relying on one.

Next: why models make things up

When Anaya’s allergy falls out of the window, the model does not say “I no longer know”. It answers fluently from what is left. Part 15 asks where such confident mistakes come from, including when the facts were never in view, and why they are so hard to stop.

AN IDEA TO TAKE WITH YOU
A model remembers nothing: before every reply it re-reads the chat through a fixed window. What falls outside is gone, what is inside costs more the longer it gets, and even inside, the middle is easiest to miss.
