Inside LLM serving: one model, millions of chats

A frontier model is one read-only copy of hundreds of gigabytes of numbers, shared by everyone. Each chat owns a small, growing pile of memory. Nearly every odd thing about AI products follows from those two facts.

Built from the study “Inside LLM Serving” (shared by the reader, Oct 2026), facts checked against the papers and spec sheets it cites

compute, weights, output memory & the KV cache waiting, waste, price wires and networks the wrong intuition

The setup

One copy, millions of chats

The weights are the model’s learned numbers: one read-only copy of hundreds of gigabytes, shared by every user. Each conversation owns only its own memory, called the KV cache. That split — shared weights, private chats — explains almost everything that follows.

The trip

A message’s short journey

Your text passes sign-in, rate limits and a router, which picks a replica: one full copy of the model spread over a group of chips. The replica reads the whole prompt in one parallel pass (prefill), then writes the answer one token per pass (decode). Only that last part is expensive.

The engine

A model only guesses words

Each pass scores every token in the model’s vocabulary. A function called softmax turns those scores into probabilities, and a sampler picks one token. Temperature sets how boldly it picks: near zero it takes the top word, higher values spread the chances.

The unit

Words become tokens

The model never sees letters. Text is cut into tokens: chunks of about four characters in English. Every limit and price is counted in them, and so is memory. In the example system, 1,000 tokens of chat hold about 160 MB of KV cache.

The building block

Inside one pass

A pass is a stack of identical layers. In each one, tokens first look at each other (attention), then each token is processed alone by a big matrix (the MLP). Both add their result to a running list, so early information survives to the end.

The mechanism

Attention looks backwards

The newest token asks a question, the query. Every earlier token offers a label (a key) and some content (a value); matches get more weight. Those keys and values never change for that chat, so the replica saves them. That saved pile is the KV cache.

The hardware

The model must fit in memory

A model’s parameters are its learned numbers. Precision is how many bits each number uses: 16-bit takes 2 bytes, 8-bit takes 1, 4-bit takes half. For 200 billion parameters, that is 400, 200 or 100 GB.

A chip holds 80–288 GB, and weights can fill at most about 60% of it; the rest is working space and other people’s caches. So even a 200 GB model is spread over several chips.

Inside the chip

A kitchen beside a warehouse

Inside a chip, a small compute die does the arithmetic, surrounded by stacks of HBM (high-bandwidth memory). HBM is the chip’s main memory: big and fast, but far slower than the tiny SRAM on the die. Tensor cores (specialised matrix multipliers) do the maths. A B200-class chip can do about 560 operations for every byte it reads from HBM.

Two workloads

Reading is parallel, writing is serial

Prefill reads the whole prompt at once: all tokens are known, so the chip runs one large matrix multiply. Decode writes the answer one token per pass, because each token depends on the last. The wait for the first token is called time to first token; the gap between later tokens is one decode step.

The analogy

The cookbook is the bottleneck

Think of a chef who must haul the entire cookbook from a warehouse for every dish. Cooking is quick; the road is slow. A decode step is that trip: it reads all the weights to make one token per conversation. Put 128 conversations on the same step and one haul makes 128 tokens. That is batching.

The trade-off

Batching shares one read

One read of the weights can serve everyone in the batch. Total output rises as the batch grows, but each person’s step gets slower and memory fills. Operators pick a point: small batches for snappy chat, large batches for cheap bulk work.

The KV cache

Each chat owns a growing pile

For every token, each layer stores a key and a value. In the example that is 160 KB per token, so an 8,000-token chat owns about 1.3 GB. The weights are shared; these piles are not. Memory, not arithmetic, caps how many chats fit.

Shrinking the cache

Share the keys and values

Attention can let several query heads share one set of keys and values. The questions stay separate; the stored answers shrink. MHA stores one pair per head, GQA one per group, and MQA one for all. MLA compresses each token into a small vector instead.

Paging and sharing

Hand out memory in blocks

Old servers reserved the longest possible answer, so most of the slab sat empty. PagedAttention (vLLM, 2023) hands out small blocks only when needed, and identical prefixes can be stored once. In the paper, real token data used just 20–38% of KV memory before paging.

Perfect packing assumed: every chat reaches its full length, with no fragmentation or activation memory. Real servers are less tidy, so treat these as ceilings.

Many chips

Four ways to cut a model

Tensor parallelism slices every matrix across chips. Pipeline parallelism gives each chip a stretch of layers. Expert parallelism spreads experts. Replication copies the whole model. The first needs the fastest wires, the second creates idle bubbles, and the third needs all-to-all traffic.

The wires

Fast inside the box, slow outside

Chips in one box talk over NVLink at hundreds of gigabytes per second; an NVL72 rack links 72 chips. Between servers, InfiniBand or Ethernet (the data-centre network) is 10–100× slower. That is why tensor splitting stays inside one fast link domain, while pipeline splitting can cross racks.

Mixture of experts

Many experts, few per token

A mixture-of-experts model keeps many small networks called experts and routes each token to a few. DeepSeek-V3 stores 671 billion parameters but uses about 37 billion per token, choosing 8 of 256 experts. At large batches, almost every expert gets read anyway.

Continuous batching

A finished chat frees its seat

Fixed batches wait for the longest answer, leaving seats idle. Continuous batching decides at every step: finished chats leave, queued ones join, and their memory is reused at once. Orca (2022) introduced iteration-level scheduling; it is now standard.

Reading versus writing

A big prompt stalls the room

A long prompt takes tens to hundreds of milliseconds of arithmetic. If it runs as one block, every mid-answer chat waits and streaming stutters. Chunked prefill splits it across steps; a separate-pool setup gives reading and writing their own chips and copies the KV cache over the network.

Smaller numbers

Fewer bits, fewer bytes

Storing each weight in fewer bits cuts the memory read almost proportionally. A 200-billion-parameter model is 400 GB at 16-bit, 200 GB at 8-bit, 100 GB at 4-bit. The cost is rounding error; block scales and keeping sensitive layers at higher precision limit the damage.

Guessing ahead

A small model drafts, the big one checks

Speculative decoding lets a small draft model guess the next few tokens, then the big model checks all the guesses in one pass. Accepted guesses cost one big pass instead of several. Rejection sampling keeps the output distribution exactly the same.

The kernel

Do not write the big grid

Attention builds a score for every pair of tokens. A naive kernel writes that grid to HBM and reads it back, which costs more time than the arithmetic. FlashAttention (2022) works through small tiles in on-chip SRAM, so the grid never lands in HBM. It is exact, not an approximation.

The front door

Queues absorb what chips cannot

A router sends each request to a pool with the right model and priority. Chat needs a fast first token and steady gaps; batch work can wait. When arrivals outrun capacity, the queue grows and waiting time explodes, so providers return an overload error (Anthropic uses 529) instead of hiding it.

The fleet

Chips fail; traffic must not notice

A large cluster is never fully healthy. Meta reported 466 job interruptions in 54 days while training Llama 3 on 16,000 GPUs — about one every three hours. Serving adds failures mid-request and weight updates. Replicas, health checks and draining let a spare take over without dropping the answer.

The bill

Idle chips still cost money

A chip costs the same whether it is busy or idle, so cost per token falls as utilisation rises. The example system at about 3,100 tokens per second can keep roughly 155 people supplied at 20 tokens per second — if every seat stays full. Batching, caching and queues exist to keep it full.

AN IDEA TO TAKE WITH YOU
Every trick in LLM serving does one of two things: share a read of the weights, or stop reserving memory you are not using.
