AI chips: GPUs, TPUs and Trainium

A GPU is a general machine that happens to be good at AI. Google’s TPU and Amazon’s Trainium were designed for AI from the first sketch. This part compares them by what each design throws away and what it adds: a different shape of arithmetic unit, smaller numbers, more memory on the chip, and faster memory beside it.

The problem

A GPU’s sums mostly come from one part

Part 5 recap: a GPU has thousands of simple workers that march in groups of 32, plus tensor cores that multiply whole blocks of numbers in one step. On NVIDIA’s H100, almost all of the AI arithmetic comes from those tensor cores public.

The ordinary workers, the warp schedulers and the caches are still there, because a GPU also has to run graphics, physics and any program someone writes in CUDA. So a natural question: if AI is almost nothing but grid multiplies, what if a chip kept only the grid unit and the memory to feed it?

The first answer

Google’s first TPU: almost no control

Google asked that question in 2013 and had a chip in its data centres by 2015: the TPU, tensor processing unit public. Its heart is one 256-by-256 grid of 65,536 multiply-and-add units working on 8-bit numbers, beside 28 MiB of memory on the chip. Its peak was 92 trillion operations a second.

Look at the purple sliver. The paper lists what the TPU left out: “no caches, branch prediction, out-of-order execution, multiprocessing, speculative prefetching, address coalescing, multithreading, context switching” public. Those are Part 4’s CPU tricks and Part 5’s GPU tricks. Its authors summed it up: “Minimalism is a virtue of domain-specific processors.”

Go deeper: why it could afford to be so simple

The first TPU only ran trained models (inference), as a plug-in card taking orders from a CPU over PCIe, the same bridge as Part 5, chapter 15. It had about a dozen instructions, and one of them, “MatrixMultiply”, could keep the big grid busy for thousands of clock ticks. With so few decisions to make, very little control was needed. Its measured speed was 15 to 30 times that of the CPUs and GPUs in the same data centres, on Google’s own models public.

The analogy

A bucket chain, not everyone at the well

Picture a fire and a well. If every helper walks to the well for each bucket, the path to the well is jammed. In a bucket chain, water leaves the well once and is passed from hand to hand, and every helper still does useful work on it.

Mapping it back: the well is memory, buckets are numbers, helpers are multiply-and-add units. Where the analogy breaks: a bucket of water is used up, but a number can be reused. Each unit multiplies the passing number, keeps a copy of nothing, and hands the same number on to the next unit, which uses it again.

How it works

A systolic array: numbers march through a grid

The TPU’s grid works like that chain, in two directions. Each cell holds one weight that stays put. A token’s numbers enter from the left and move one cell right per tick. Running sums move one cell down per tick. The name systolic comes from the heart: data pulses through in step public. Here it is with Part 5’s two 4-by-4 grids:

Press Step a few times. The answers match Part 5’s grid multiply exactly, but no cell ever went to memory: the 16 weights were loaded once and the 16 input numbers each entered once. Every number was then used four times, once in each cell it passed.

Go deeper: the timing rule

Token i’s number for row k enters at tick i + k. It reaches the cell in column j at tick i + k + j, where it is multiplied by that cell’s weight and added to the sum arriving from above. The sum for answer (i, j) leaves the bottom after tick i + j + 3. The staggered start is what lines everything up, which is why the input queue on the left looks like a staircase. A real TPU grid works the same way at 128 or 256 cells a side public.

Why bother

Bigger grids reuse each number more

Part 8 showed that fetching a number costs more than multiplying it. The TPU paper says the same about its own on-chip memory: “reading a large SRAM uses much more power than arithmetic” public. In an n-by-n grid, each number fetched is used n times. So the bigger the grid, the fewer fetches per sum.

Google’s 2023 TPU v4 paper makes exactly this comparison: its 128-by-128 grids reuse each input 128 times, “whereas the 4x4 FP16 array multipliers of the A100 only get reused 4 times, leading to more on-chip SRAM accesses” public. Newer GPU tensor cores handle larger blocks than the A100’s, but NVIDIA does not publish their internal grid size not public.

The catch

Big grids waste cells on awkward sizes

A grid unit only works in whole tiles of its own size. The first TPU paper tested a 600-by-600 matrix from one of its models. On the 256-by-256 grid it took 9 tiles; on a hypothetical 512-by-512 grid it took only 4, but each was four times slower, so the bigger grid lost public.

This is the trade every designer weighs: big grids save memory trips, small ones waste less on odd shapes. Google’s TPUs from v2 to v5p used 128-by-128 grids, several per chip; its two newest generations went back to 256 by 256 public.

Smaller numbers

How a number is packed into bits

Part 5 showed that fewer bits per number means more sums per second. A floating-point number has three parts: a sign, some range bits (how big or small it can be, like the power of ten in 3 × 10⁸), and some detail bits (how many digits it keeps). Each format splits its bits differently:

bfloat16 (“brain floating point”) is Google’s format. It keeps all 8 of FP32’s range bits and throws away detail instead: “the dynamic range of bfloat16 is identical to that of FP32” public. Neural networks tolerate rough numbers far better than numbers that overflow, so this turned out to be the right thing to cut.

Why it pays

Detail bits cost silicon, squared

Part 3 showed a multiplier is a grid where every bit of one number meets every bit of the other. So its size grows with the square of the detail bits. Google: bfloat16 multipliers are “about half the size in silicon of a typical FP16 multiplier, and they are eight times smaller than an FP32 multiplier” public.

Counting the hidden leading 1 that every format keeps, the squares are 24², 11², 8² and 4². That rough rule gives a ninth for bfloat16 against FP32, close to Google’s “eight times” example. The answers are still added up in 32 bits, so small rounding errors do not pile up across thousands of additions public. The first TPU went further, to 8-bit whole numbers, which its paper says can take 6 times less energy and area than 16-bit floating point public.

The march down

Eight bits, then four, with shared scales

NVIDIA’s H100 added two 8-bit floating-point formats, E4M3 and E5M2 (4 or 5 range bits), with hardware that picks 8 or 16 bits layer by layer public. Blackwell GPUs added 4-bit numbers. A 4-bit number has only 15 distinct values, so blocks of numbers share one extra scale that stretches the steps to fit the block.

In NVIDIA’s NVFP4, every block of 16 numbers carries its own 8-bit scale, plus one 32-bit scale for the whole grid; the shared MXFP4 format uses blocks of 32 public. The dots that miss their step are the rounding error. Whether a model still works this rough is tested model by model.

Who gets what

Not every chip doubles at fewer bits

Each designer decides which formats get their own fast path. Here is the peak speed of each chip at 16, 8 and 4 bits, from the companies’ own spec pages public:

NVIDIA doubles the speed at each halving it supports. Google’s Trillium (TPU v6e) runs 8-bit floating point at the same speed as bfloat16; Ironwood doubles it. AWS’s Trainium3 does 8-bit and 4-bit at the same speed, so for it 4 bits saves memory, not maths. These are choices about where to spend switches, not signs of a better or worse chip.

Memory on the chip

Every design adds memory on the chip

Part 8 showed memory beside the chip is far slower than memory on it. So all three families spend a lot of silicon on SRAM, the fast memory built into the chip itself. They differ in how they use it public:

A GPU spends a big share on registers, the private scratch space of every worker, because it hides waits by keeping thousands of groups ready (Part 5, chapter 7). TPU v4 has one thread per core and a register file of 0.25 MiB; the TPU paper contrasts that with an A100 GPU’s 27 MiB public. TPUs and Trainium instead have big memories the software fills on purpose: AWS calls Trainium’s 28 MB per core “software-managed” public.

Memory beside the chip

Every generation buys faster HBM

On-chip memory holds a grid, not a model: Part 5’s 8-billion-number model is 16 GB at 16 bits. That lives in HBM, the stacked memory right beside the chip that Part 8 introduced. The first TPU used plain DDR3 memory instead, and paid for it:

Its paper found most of its models waiting on that 34 GB/s, and estimated that the GPU’s faster memory “would triple achieved TOPS” public. Every later chip in all three families bought HBM, and each generation buys more of it. How the chips talk to each other is a separate road, covered in Part 12.

The yardstick

Is the chip waiting for maths or memory?

Put the two speeds together. Divide a chip’s sums per second by its bytes per second and you get its ridge point: how many sums it must do with each byte it reads to keep the arithmetic busy. Below that, it waits on memory. Above it, the maths is the limit public.

Take Part 5’s 4,096-by-4,096 weight grid at 16 bits. One token does one multiply and one add with each 2-byte weight: 1 sum per byte, far left. Push 64 tokens through the same weights and each byte serves 64 tokens; at 1,024 tokens the chip finally runs out of arithmetic example. This drawing is called a roofline; the first TPU paper used it to explain every one of its results.

Try it

One multiply of Part 5’s 4,096-by-4,096 weight grid by a stack of tokens. Pick how many tokens go through together, the number format, and the chip. The orange bar is the time if only the arithmetic counted, the teal bar the time if only memory traffic counted. The real time is roughly the longer one.

Try one token at 16 bits on every chip: all are memory-bound, by 100 times or more, whatever their logo. Then raise the tokens: the teal bar barely moves, because the weights are read once however many tokens share them, while the orange bar grows. Fewer bits shrink both bars, which is why every family keeps adding smaller formats.

Go deeper: exactly what the lab computes

With n = 4,096 and t tokens: sums = 2 × t × n² (a multiply and an add per weight per token); numbers moved = n² weights + t × n inputs + t × n outputs, all in the chosen format; maths time = sums ÷ the chip’s dense peak for that format; memory time = bytes ÷ the chip’s memory bandwidth. Where a chip lists no 4-bit speed, numbers are stored in 4 bits but multiplied at its 8-bit speed example. It assumes perfect overlap and peak speeds, which real chips never reach (chapter 16), and ignores on-chip reuse across grids. Spec figures: H100 989.5 / 1,979 trillion, 3,350 GB/s; B200 2,250 / 4,500 / 9,000, 8,000 GB/s; Ironwood 2,307 / 4,614, 7,380 GB/s; TPU v4 275 / 275, 1,200 GB/s; Trainium2 667 / 1,299, 2,900 GB/s; Trainium3 671 / 2,517 / 2,517, 4,900 GB/s public.

The surprise

Different logos, nearly the same balance

Three companies, three design philosophies. Yet divide each chip’s 16-bit speed by its memory speed and the ridge points land close together: roughly 140 to 310 sums per byte public.

That is not an accident. Arithmetic is cheap to add and memory speed is expensive, so every designer adds sums until memory can just about keep up with a busy server, and no further. The first TPU’s ridge point was 1,350, far to the right, and it spent most of its time waiting. For a single chat, at 1 sum per byte, every one of these chips is waiting on memory.

The common mistake

The biggest headline number does not win

Spec sheets print peak numbers, and often the biggest version of them. NVIDIA’s H100 page lists 1,979 trillion for 16 bits, with a footnote: “With sparsity” public. That counts a trick where half of the weights in each small group are forced to zero and skipped. For ordinary dense maths, the peak is half: about 990 trillion.

And a peak is a ceiling, not a speed. The first TPU paper measured its six real workloads: they used 6% to 78% of the chip’s peak, 23% on average public. Comparing chips by headline numbers ignores memory, number formats, sparsity footnotes and software. Fair comparisons run the same model on both, and companies rarely publish those for each other’s chips.

Side by side

Three repeated building blocks

Each chip is one building block, copied. An H100 repeats a GPU block (an SM) 132 times. A TPU v4 has two TensorCores, each with four 128-by-128 grids and a vector unit, sharing 128 MiB of memory. A Trainium2 has eight NeuronCores public.

A NeuronCore has a tensor engine “based on a power-optimized systolic array”, plus vector, scalar and fully programmable engines for everything that is not a grid multiply public. Amazon’s Inferentia chips are the inference-only siblings: Inferentia2 uses the same cores as the first Trainium, 190 trillion sums a second at 16 bits public. Block sizes in the drawing are illustrative example.

So what

Next: why bigger keeps working

Every design on this page exists because bigger models, trained on more data with more arithmetic, kept getting better, and the bill for that arithmetic became worth a custom chip. Part 11, back on the LLM track, shows the surprisingly steady rules behind “bigger works”. Part 12 then shows how thousands of these chips are wired together to act as one.

AN IDEA TO TAKE WITH YOU
A GPU, a TPU and Trainium all make the same bet: bigger grids of multipliers, fewer bits per number, more memory on the chip and faster memory beside it. They differ in what they keep from general computing, and none of them escapes the cost of reading the weights.
