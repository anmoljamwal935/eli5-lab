Text becomes numbers

A computer can only do arithmetic. So before an AI model can read a single word of your message, the words have to become numbers. This part shows how: first the text is cut into pieces, then each piece is swapped for a list of numbers that works like a position on a map of meaning.

Facts carry a tag. public means a published paper, spec sheet or plain arithmetic. example means a made-up but consistent number, used to show how something works. not public means the company has not said. The Go deeper boxes are optional.

The problem

A computer only understands numbers

Everything inside a computer is stored as numbers. A photo is a grid of dots, and each dot is three numbers: how much red, green and blue. A song is a long list of numbers saying how far the speaker should push the air, forty-four thousand times a second. Text is no different. It has to be numbers too.

An AI model is a giant calculator. It takes numbers in, does a huge amount of multiplying and adding, and gives numbers out. So the first question of the whole series is simple: which numbers should stand for words? The answer has two steps, and this part covers both: cut the text into pieces, then give every piece a list of numbers that captures what it means.

First try

Give every letter a number

The obvious idea already exists. Every letter, digit and symbol has an agreed number, set by a worldwide standard called Unicode. Lowercase a is 97, b is 98, c is 99. It covers about 150,000 characters public, from English and Hindi to Chinese and emoji. Type below and see the numbers your computer already uses:

Type anything

This works, and it is how text is stored on disk. But it is a poor way to feed a model, for two reasons. It is long: a 1,000-word essay is about 5,000 letters, and later parts show the model does real work for every single piece it reads and writes. And the numbers mean nothing: 97 and 98 sit next to each other, yet “a” and “b” have nothing in common. Worse, a model might believe they do.

Go deeper: characters versus bytes

Two layers of numbers. Unicode gives each character one number, called a code point: “é” is 233, the Hindi letter “न” is 2,344, the pizza emoji is 127,829. To store those on disk, a scheme called UTF-8 writes each code point as one to four small numbers between 0 and 255, called bytes.

English is cheap in bytes. Plain English letters take one byte each. Accented letters take two, Hindi and most Indian scripts take three, and emoji take four. This detail comes back later: many tokenizers start from bytes, so text in some scripts starts out several times longer.

Second try

Give every word a number

So try the opposite: a big numbered dictionary of whole words. “the” is 1, “cat” is 2, and so on. Now a sentence is short, one number per word. But three new problems appear.

Typos, new slang, product names, a word in another language: none of them are in the list, so the model would see only a blank “unknown” marker and lose the word entirely.

The middle path

Cut text into reusable pieces

The answer every modern model uses sits between letters and words. Keep a list of pieces. Common words get one piece each. Rare words are built from smaller pieces that are reused everywhere, like “un”, “follow” and “ed”. And the list always contains every single byte, so even a string of nonsense can be spelled out piece by piece. Nothing is ever unknown.

Each piece is called a token, and the list of all pieces is the model’s vocabulary. Notice the ␣ marks: the space before a word usually belongs to the piece, so “ cat” and “cat” at the start of a sentence can be different tokens. In English, one token is about four characters, or three quarters of a word, on average public.

Go deeper: real vocabulary sizes

Lists are tens of thousands of pieces long. public GPT-2 used 50,257 tokens. Llama 2 used 32,000; Llama 3 grew to 128,256, partly to handle more languages and code efficiently. OpenAI’s GPT-4 tokenizer has about 100,000. not public Claude’s tokenizer and its size.

Special tokens. A few entries are not text at all: markers meaning “end of text” or “a new message from the user starts here”. They let the model tell where one part of a conversation ends and the next begins.

Bigger is not simply better. A longer list makes text shorter in tokens, but every entry needs its own row of numbers inside the model (chapter 16), and rare entries are seen too seldom in training to learn well.

Building the list

Glue the most common pair, again and again

Nobody writes the piece list by hand. A program builds it from a huge pile of sample text with one simple rule. Start with single letters. Count every pair of neighbours. Glue the most common pair into a new piece and add it to the list. Repeat, tens of thousands of times.

After a few steps, “est” and “low” and “new” exist as pieces, because they kept turning up. Run this on billions of words and the list fills with whole common words, common endings like “ing” and “tion”, and pieces of names. This method is called byte-pair encoding, or BPE public: it began as a way to compress files in 1994 and was adopted for language models in 2016.

Go deeper: the details that matter

Starting from bytes. Most modern tokenizers start from the 256 possible bytes rather than letters (chapter 2). That is why nothing is ever unknown: any text in any script is some sequence of bytes.

Splitting first. Before counting pairs, text is split at spaces and punctuation, so a piece never glues the end of one word to the start of the next. Digits are often handled specially, for example cut into groups of up to three.

Using the list. To cut new text, the tokenizer replays the glue steps in the order they were learned. Ties and the exact splitting rules differ between tokenizers, which is why two models can cut the same sentence differently. Other methods exist (WordPiece, Unigram), but they share the idea: frequent text gets big pieces, rare text gets small ones.

At 256 pieces the list holds only bytes, so English text is one token per letter. As pieces are added the count drops fast, then more slowly. Dashed boxes are lone bytes that are only part of a character: this small list never saw Hindi or emoji, so it spells them out byte by byte.

Go deeper: what is different in a real one

Training text. Real tokenizers learn from billions of words across many languages and a lot of code, so their pieces are much more general. This one learned only from this page, so it knows “tokens” and “numbers” very well and almost nothing else.

Size. This list stops at 1,256 pieces; real ones have 30,000 to 200,000 (chapter 4). The rule is exactly the same.

The ID numbers. IDs 0 to 255 are the bytes. Every glued piece gets the next free number, in the order it was learned, so a low ID means the piece was found early, because it is very common.

The hand-off

The model only ever sees ID numbers

Once text is cut, each token is replaced by its position in the list: its ID. Your message reaches the model as nothing but a row of whole numbers. The model never sees a letter. When it answers, it produces IDs too, and the app looks each one up in the same list to turn it back into text for your screen.

Go deeper: a chat is one long row of IDs

Everything is tokens. The app’s hidden instructions, your earlier messages, the model’s earlier replies, and your new message are all joined into one long row of IDs, with special tokens marking who said what. The model reads that whole row every time.

Why this matters for cost. Usage limits, prices and the longest conversation a model can handle are all counted in tokens, not words. That is the subject of part 14 of the series.

The gotcha

Why a model can miscount letters

Ask a model how many letter r’s are in “strawberry” and older models often got it wrong. Now you can see one big reason. The model does not receive the letters s-t-r-a-w-b-e-r-r-y. It receives a few token IDs, and an ID is just a number. To count letters it would have to have learned, separately, how each of its tokens is spelled.

The same blind spot explains other old stumbles: spelling a word backwards, finding rhymes, and arithmetic on long numbers, which can be cut into odd chunks like “123” and “4567”. Newer models do much better, because they have learned a lot about spelling and some can work step by step (part 16). But the root cause is the cutting.

Not all text is equal

The same message can cost very different amounts

A piece list is built from its sample text, so it is efficient for whatever that sample had most of. Text it saw rarely gets cut into many small pieces. Here is this page’s tokenizer, trained only on English, cutting the same short greeting in different forms:

Real tokenizers learn from many languages, which narrows the gap but does not close it. A 2023 study found the same text could need up to 15 times more tokens in some languages than in English public. That matters, because people pay per token, wait per token, and hit length limits counted in tokens.

Go deeper: turning tokens into money

A rule of thumb for English. 1,000 words is roughly 1,300 tokens. An API priced at $3 per million input tokens example would charge about 0.4 cents to read a 1,000-word document.

Why tokenizers keep growing. Part of the reason Llama 3’s list grew to 128,256 pieces public was to give more languages and code their own common pieces, so they take fewer tokens.

Half done

An ID is a name tag, not a meaning

Cutting text and numbering the pieces solves the first job. But an ID is like a locker number. Locker 902 and locker 903 are neighbours, and what is inside them has nothing to do with each other. In the same way, “cat” might be ID 902 and “kitten” ID 74,311, even though they mean nearly the same thing.

If the model did arithmetic on the IDs themselves, it would believe “cat” (902) is almost the same as whatever happens to be 903. So the second job is to swap each ID for numbers that do carry meaning.

The analogy

A map of meaning

Imagine placing every token on a map, so that tokens used in similar ways sit close together. Animals end up in one corner, foods in another, vehicles in a third. Now a token’s numbers are simply its position on the map: how far across, how far up. “cat” and “kitten” get almost the same numbers, because they sit side by side.

Tap any word to see its three nearest neighbours.

Mapping it back. The map is the model’s table of numbers; a word’s spot is its list of numbers; distance on the map is how different two meanings are. Where the analogy breaks: this map has two directions, across and up. A real model’s map has thousands, which no one can picture. The positions here are hand-placed example values.

Thousands of directions

Each token gets a long list of numbers

Two numbers can only separate a few kinds of meaning. Real models give every token a list of thousands: 4,096 numbers in Llama 3 8B, 12,288 in GPT-3 public. Each number is one direction on the map. The list is called the token’s embedding: the word is “embedded” as a point in a space with thousands of directions.

Below, each bar is one number in a 48-number list example; up is positive, down is negative. Similar words get similar patterns.

No single number cleanly means “is an animal” or “is plural”. Meaning is spread across many of them at once, the way a face is not stored in one pixel. That is one reason models are hard to look inside.

Go deeper: how many numbers, and why

Sizes in public models. public GPT-2 small: 768 numbers per token. Llama 3 8B: 4,096; Llama 3 70B: 8,192. GPT-3: 12,288. More numbers give room to separate more shades of meaning, at the cost of more memory and arithmetic everywhere in the model.

Precision. Each number is usually stored with 16 bits (2 bytes). A token’s list of 4,096 numbers is therefore 8 KB.

Directions carry meaning

Arithmetic on meaning

Something surprising happens on these maps. The step from “man” to “woman” points in roughly the same direction as the step from “king” to “queen”. So you can do sums with meaning: start at king, subtract man, add woman, and you land near queen. This was shown with an early word map called word2vec in 2013 public.

CHOOSE A SUM

The honest version. It works for famous examples and fails for many others. Usually the nearest point to the sum is one of the words you started with, so those are ruled out by convention. It is a real tendency, not a law. But it shows that directions, not just positions, carry meaning: one direction roughly means “female version of”, another “capital city of”, another “past tense of”.

Measuring closeness

How a model compares two lists of numbers

Think of each list as an arrow from the centre of the map to the word’s spot. Two arrows pointing the same way mean similar meanings. Arrows at right angles mean unrelated. Opposite arrows mean opposite. Turn one arrow and watch the score:

ANGLE BETWEEN THE ARROWS

The way to get that score from two lists is pure arithmetic: multiply the two first numbers together, the two second numbers together, and so on, then add everything up. Matching signs push the total up, clashing signs pull it down. This is called the dot product. Scaled so the result runs from −1 to +1, it is called cosine similarity. The same multiply-and-add appears again in part 7, where it is how each word decides which other words to pay attention to.

Go deeper: the sum, worked out

Take three-number lists example: cat = (0.8, 0.1, 0.5), kitten = (0.7, 0.2, 0.6), car = (−0.2, 0.9, 0.1).

cat · kitten = 0.8×0.7 + 0.1×0.2 + 0.5×0.6 = 0.56 + 0.02 + 0.30 = 0.88 cat · car = 0.8×(−0.2) + 0.1×0.9 + 0.5×0.1 = −0.16 + 0.09 + 0.05 = −0.02

Cat and kitten score high; cat and car score about zero. Cosine similarity divides the dot product by the two arrows’ lengths, so only the direction counts, not how long the arrows are.

Where else it is used. Search engines and “find similar documents” features turn text into lists of numbers this way and compare them with exactly this score.

Where the map comes from

Nobody draws the map. Training does.

No person decides where “kitten” goes. Every token’s list starts as random numbers, so the map starts as a meaningless scatter. During training (part 6), the model reads enormous amounts of text and keeps being nudged to guess the next word better. Words that appear in similar sentences get nudged towards similar positions, because that helps the guessing. Slide to watch a scatter settle into a map:

AMOUNT OF TRAINING

This is an illustration example: real training moves thousands of numbers per token at once, over weeks. But the principle is old. In 1957 the linguist J. R. Firth wrote, “You shall know a word by the company it keeps.” public A model learns a word’s meaning only from which words keep turning up around it.

The lookup table

One row of numbers per token

Inside the model, the map is stored as a giant table, the embedding table. It has one row for every token in the vocabulary, and each row is that token’s list of numbers. The very first thing a model does with your message is look up the row for each ID. That is the whole of step one: no thinking, just looking up.

Go deeper: the table appears twice

At the end, too. When the model finishes its calculation, it has to score every token in the list as the possible next word (part 2). That needs another table of the same shape. Some models, GPT-2 among them public, simply reuse the same table for both ends to save memory.

Why vocabulary size costs memory. Doubling the list from 64,000 to 128,000 pieces doubles both tables. That is one reason lists are not made endlessly long.

The limitation

One word, many meanings

The table gives each token one fixed row. But “bank” in “the river bank” and “bank” in “bank account” are the same token, so they start from exactly the same numbers. The table cannot tell them apart.

Fixing this is the job of the rest of the model. Layer by layer, each token’s list is adjusted using the tokens around it, so “bank” next to “river” drifts towards water and “bank” next to “account” drifts towards money. How the words share that information is part 7, attention. The table is only the starting point.

One more missing piece

Order matters, and the table ignores it

“Dog bites man” and “man bites dog” contain exactly the same three tokens, so the table hands back exactly the same three lists. Yet the meanings are opposite. So the model also needs to know where each token sits in the row.

Modern models mix position into the calculation, so a token “knows” it is first, second or third. The common method today does it by gently rotating the numbers by an amount that depends on position. That is covered properly in part 7, next to attention, because that is where position is used.
